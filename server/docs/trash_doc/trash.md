# Trash 功能开发计划

## 1. 目标与边界

为文档和文件夹增加回收站：删除后保留 30 天，支持列表、恢复、单项彻底删除及到期自动清理。

已确定的规则：

- 按**当前项目写权限**管理回收站；成员退出或权限收回后立即失去访问权限。
- 删除项目仍是彻底删除，`cascade=true` 同时清理该项目内的回收站内容。
- 文档恢复到原文件夹；原文件夹已进入回收站时，必须先恢复文件夹。
- 回收站期间禁止分享访问；恢复后，未撤销的旧分享链接重新有效。
- 本期仅开发后端；不增加前端页面、批量操作、清空整个回收站或独立附件回收功能。

## 2. 数据与业务实现

**数据结构**

- 在 `documents`、`folders` 增加可空字段 `deleted_at`、`deleted_by`、`expires_at`，以及到期清理、项目列表查询所需索引。
- 当前完整字段和索引保存在 `internal/database/schema.sql`，仅供空库初始化；开发阶段已有数据库由开发者显式维护，不使用 `AutoMigrate`。
- 已有记录默认处于正常状态；保持原 ID、公开 key、正文、附件关联和分享记录。

**进入回收站与恢复**

- 现有文档、文件夹 DELETE 接口改为软删除，成功响应继续使用 `{success:true}`。
- 文件夹含正常文档时仍要求 `cascade=true`；删除文件夹只标记文件夹，其正常文档随父级隐藏，不逐条建立回收站记录。
- 先独立删除文档、再删除文件夹时，保留文档原删除时间和到期时间。恢复文件夹只恢复随父级隐藏的文档，独立删除的文档仍留在回收站。
- 删除和恢复保持原内容修改时间、修改人及 revision；重新删除已恢复对象时重新计算 30 天期限。
- 文件夹彻底删除会删除其中全部文档，包括此前独立进入回收站的文档；项目彻底删除同样包含正常内容与回收站内容。

**查询与权限**

- 普通文档查询统一要求文档和所属文件夹均未删除；文件夹列表、查找和默认文件夹选择也排除已删除记录。
- 覆盖项目树、搜索、详情、正文读写、附件操作、最近文件和分享入口，防止通过其他接口访问回收站内容。
- 最近查看记录保留并隐藏，恢复后仍存在的记录可重新显示，不新增查看时间。
- Trash 使用专用查询读取删除记录，每次操作重新检查项目写权限。
- 复用现有写事务与 `workspace_state` 锁，使删除、恢复、保存和到期清理串行校验状态。

## 3. 接口约定

新增接口均要求登录：

| 方法 | 路径 | 行为 |
|---|---|---|
| GET / HEAD | `/api/trash` | 分页查询有项目写权限的回收站内容 |
| POST | `/api/trash/:type/:key/restore` | 恢复单项 |
| DELETE | `/api/trash/:type/:key` | 彻底删除单项 |

- `type` 仅接受 `document`、`folder`；`key` 使用现有 `file_key` 或 `folder_key`。
- 列表支持 `team_key`、`project_key` 过滤；未指定团队时沿用现有个人团队默认规则。分页使用 `limit`、`offset`，默认 50、0，`limit` 最大 200。
- 返回 `{items,total,limit,offset}`；在权限过滤后统计与分页，按 `deleted_at DESC,type,key` 稳定排序。
- 每项包含类型、公开 key、名称、团队与项目 key、原文件夹 key、删除人、删除时间、到期时间、`can_restore`；文件夹附带文档总数。正文与附件内容不在列表中返回。
- 独立删除的文档单独展示；随文件夹隐藏的文档不重复展示。
- 参数错误返回 400；不存在或无权限返回 404；恢复正常对象、尚未恢复原文件夹、删除正常对象等状态冲突返回 409。
- 到期记录不再展示或允许恢复；尚未物理清理时恢复返回 409，已清理则返回 404。恢复和彻底删除成功均返回 `{success:true}`。

## 4. 自动清理与存储

- 在应用生命周期内启动清理 worker：启动后异步扫描一次，此后每小时扫描，处理期限为删除后 30 × 24 小时。
- 每批读取最多 100 个到期对象，每个对象独立事务，并在锁内重新检查删除状态及到期时间；已恢复或已删除的对象跳过。
- 清理失败回滚该对象、记录错误并在下一轮重试；后台异常不得导致服务退出。关闭服务时取消并等待 worker，再关闭数据库。
- 文档彻底删除复用现有附件关联删除和数据库级联；文件夹先删除文档，再删除文件夹。
- **沿用当前 R2 策略：只清理数据库记录，保留共享哈希对象。** 本期不增加孤儿对象清理，因此“彻底删除”不保证释放 R2 空间。
- 日志记录清理数量、耗时及错误类型，便于发现持续清理失败。

## 5. 开发顺序与验收

1. 维护初始化 SQL、模型字段和 Trash Repository。
2. 实现软删除、恢复、彻底删除及普通查询过滤。
3. 注册接口，接入清理 worker，更新路由、数据库和 Trash API 文档。
4. 完成构建、静态检查及隔离数据库 HTTP 冒烟验证。

验收覆盖：

- 文档删除、恢复、彻底删除；正文、附件、原 key 和分享链接行为符合约定。
- 非空文件夹的 `cascade` 校验，以及“文档先删除、文件夹后删除”的独立恢复和到期行为。
- 项目级联删除同时清理回收站，`cascade=false` 仍将回收站内文件夹视为子项。
- 项目树、搜索、最近文件、详情、附件、分享及 HEAD 均无法访问删除内容。
- 跨团队访问、成员退出、项目权限变化及分享用户尝试管理 Trash。
- 30 天边界、停机后补清理、重复扫描、清理失败重试及恢复与清理竞争。
- 空库初始化 SQL 的字段和索引与业务模型一致；使用构建、`go vet`、`go mod verify` 检查。

遵守项目约束：不生成、修改或运行单元测试；保留当前未提交改动，不升级依赖。若进入服务器开发阶段，通过 SSH 在服务器直接修改，不上传本地代码。
